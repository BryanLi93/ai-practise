# 核心技术决策

这里只保留会影响系统设计的选择。每一节回答三个问题：**选了什么、为什么、付出了什么代价。**

## 1. 用 PostgreSQL 同时保存业务数据、向量和全文索引

**选择**

- 文档、chunk、会话和消息都存在 PostgreSQL。
- 向量使用 pgvector，中文全文检索使用 `tsvector + zhparser + GIN`。
- `content_tsv` 是 Generated Column，由数据库根据 chunk 内容自动维护。

**原因**

项目同时需要关系数据、向量检索和关键词检索。放在同一个数据库里，事务、关联查询和运维都更直接，也能在一个服务内完成混合检索。单独引入 ChromaDB 或把关键词语料加载进 Python 内存，对当前规模没有明显收益。

**代价**

zhparser 需要自定义 PostgreSQL 镜像编译安装；当前 embedding 列还没有 HNSW 索引，数据量变大后必须补索引或重新评估检索方案。

## 3. 先用 500 字符分块，暂不做复杂文档结构识别

**选择**

使用 `RecursiveCharacterTextSplitter`，优先按段落、换行和中英文标点切分；默认 `chunk_size=500`、`chunk_overlap=50`。

**原因**

这是一个容易理解和验证的起点：chunk 不会太长，能控制送给 embedding 和 LLM 的内容量；按自然边界切分，也比固定位置截断更少破坏句子。

**代价**

500/50 只是经验值，没有经过评测调优。overlap 主要在超长段落被继续切碎时生效；普通短段落合并后不一定有重叠。Markdown 标题还可能被切成没有正文的孤立 chunk，扫描 PDF 也没有 OCR。

## 4. 检索使用“向量 + 中文关键词 + RRF”

**选择**

向量路按余弦距离排序，关键词路用 zhparser 分词后按 `ts_rank_cd` 排序。两路各取最多 80 个候选，再用 RRF 合并排名并保留前 20 个。

**原因**

向量检索擅长语义相近，关键词检索擅长专有名词、型号和代码符号。两路原始分数含义不同，直接相加需要人为归一化；RRF 只使用排名，更稳定，也更容易解释。

**代价**

混合检索多一次数据库查询。目前两路查询还是顺序执行，不是真正并行；而且当前测试知识库较小，混合检索带来的提升还没有经过系统评测证明。

## 5. 召回后预留 rerank，但默认关闭

**选择**

RRF 的前 20 个候选可以交给 `BAAI/bge-reranker-v2-m3` 精排，再取最终 `top_k`。模型通过 SiliconFlow `/v1/rerank` 调用，不在本地加载。

**原因**

向量召回使用 bi-encoder，问题和文档可以分开编码并建立索引，速度快但判断较粗。reranker 属于 cross-encoder，会同时看问题和文档，相关性判断更细，但无法预先计算全库结果。因此合理的流程是先宽召回，再只精排少量候选。

**代价**

远程 rerank 会增加一次网络往返、延迟和费用，也引入新的失败点。当前 `ENABLE_RERANK=False`，默认流程并未真正执行这一层；面试时不能说成已经默认启用。

## 6. 通过 prompt 和来源编号限制生成

**选择**

- system prompt 要求模型只能根据当前 context 回答，信息不足时固定拒答。
- 每个 chunk 编号为 `[n]`，答案必须标相同编号；API 同时返回完整 `sources`。
- 生成温度设为 0.1，并关闭 Qwen 的 `enable_thinking`。

**原因**

RAG 的目标是忠实复述知识库，而不是自由创作。低温度和明确规则可以减少发挥；来源编号让用户能够回到原文检查。Qwen 的思考内容会占用 `max_tokens`，曾导致最终 `content` 为空，所以当前生成和查询改写都关闭思考模式。

**代价**

prompt 只能降低幻觉，不能保证引用正确。`[n]` 也只是模型输出的文本约定，仍需要评测检查“答案是否真的被对应来源支持”。

## 7. 多轮对话中，改写句用于检索，用户原话用于生成

**选择**

- 会话历史保存在服务端，读取最近 6 条消息。
- 有历史时，先把含指代或省略的问题改写成独立问题。
- 改写句只用于 embedding、检索和 rerank；生成阶段仍使用用户原话和历史。
- 历史答案中的旧 `[n]` 会被删除，历史不能作为本轮事实来源。

**原因**

检索器本身没有对话状态，需要完整问题才能召回正确内容。但问题改写是一次有损转换，可能误解用户；生成阶段已经能看到历史，没有必要再依赖改写句。

**代价**

多轮问题会多一次 LLM 调用，增加延迟、token 和失败概率。这里只保留短窗口，没有做长对话摘要。

## 8. 外部调用成功后，再一次性保存问答

**选择**

读取历史、问题改写、检索和生成阶段都不写数据库。全部成功后，再创建会话并保存 user、assistant 两条消息，最后一次 `commit`。

文档入库也采用同样思路：先 `flush` 得到 `document.id`，创建全部 chunk 后再 `commit`。

**原因**

一次用户操作应该对应一个事务结果。外部 API 中途失败时，不应留下空会话、孤儿文档或半条问答；同时也不应该为了等待几秒的 LLM 调用，长期占着一个已开始写入的数据库事务。

**代价**

流式生成必须等完整答案生成后才能落库。客户端中途断开时，是否继续生成和保存还没有专门的取消策略。

## 9. 流式协议使用 SSE，语义帧和 HTTP 编码分层

**选择**

service 产生 `sources -> token -> done` 三类字典帧，router 再编码成 SSE。前端用 `fetch + ReadableStream` 读取，因为请求是带 JSON body 的 POST。

**原因**

service 不需要知道 SSE 文本格式，更容易测试和复用。先发 sources，再逐 token 发送答案，前端可以同步展示引用和生成过程。

**代价**

开流后 HTTP 状态码不能再改变，因此 router 必须先拉取生成器第一帧，把会话校验和检索错误留在开流前处理。前端也必须自己缓冲网络数据并按 `\n\n` 拆帧。

## 10. Redis 缓存只做可安全降级的两类数据

**选择**

- 问题 embedding 缓存 7 天，key 包含模型、维度和文本哈希。
- 无历史的首轮答案缓存 1 小时；多轮对话和自定义 system prompt 不复用这类缓存。
- Redis 读写失败只记日志，按缓存未命中处理。

**原因**

embedding 是稳定的纯函数结果，适合长时间复用。首轮答案也能明显减少重复检索和生成，但带历史的回答依赖上下文，不能只按当前问题做 key。缓存不应成为主链路的强依赖。

**代价**

答案缓存没有知识库版本，也没有在上传新文档后主动清理，只靠 1 小时 TTL，可能短暂返回旧答案。相同冷 key 并发请求也没有做防击穿。

## 11. 可观测性先覆盖请求主链路

**选择**

- structlog 输出结构化日志，用 `contextvars` 给每个请求绑定 `trace_id`。
- Prometheus 记录请求量、请求延迟、token、估算成本、召回候选数和 rerank 分数。
- 服务、PostgreSQL 和 Redis 由 Docker Compose 编排。

**原因**

RAG 同时依赖数据库和多个模型 API，只看最终 500 很难排错。`trace_id` 能串起一次请求，指标能观察整体延迟和调用量；容器编排保证本地环境可重复启动。

**代价**

目前只有请求级耗时，没有 rewrite、retrieve、rerank、generate 的分段耗时；也没有接入 Prometheus 服务和 Grafana 看板。成本表里部分模型还是占位单价，当前数据只能验证指标链路，不能当真实账单。
